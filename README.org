* Overview

/bisos.fileObj/ is an *umbrella package for filesystem-directory-backed
data structures* in BISOS. Each module inside is a self-contained
abstraction whose identity and state live in a filesystem directory, not
in a database or in memory.

Currently:

- =bisos.fileObj.fto= --- *File Tree Object* + tree walker. A generalization
  of the bash-based FTO facility (=/bisos/core/bsip/bin/lcnObjectTree.libSh=,
  =seedFtoCommon.sh=, =ftoProc.sh=). Marker-file conventions (=_tree_=,
  =_treeProc_=, =_objectType_=), branch/leaf classification, and a walker
  that recurses down a tree applying a command at each node. This is the
  first module and the reason the umbrella package exists.
- =bisos.fileObj.fp= --- *File Parameter*. Currently in =bisos.b.fp=;
  reserved slot for a future migration into this package.
- =bisos.fileObj.fv= --- *File Variable*. Currently in =bisos.b.fv=;
  reserved slot for a future migration.

/bisos.fileObj/ is a python package that uses the [[https://github.com/bisos-pip/pycs][PyCS-Framework]].

* Charter --- Scope of This Package

*This package is for filesystem-directory-backed data structures where the
directory IS the object identity.* If your thing needs a database, an
in-memory structure, or a network resource, it doesn't belong here.

The charter is deliberately narrow so the umbrella does not become a
"small utility drawer." Additions require that the thing being added:

1. Represents its identity and state as a filesystem directory.
2. Uses marker files (like =_tree_=) to make its type / role discoverable.
3. Sits at a similar level of abstraction as =fto=, =fp=, =fv= --- primitive
   data structures, not higher-level constructs. Higher-level things
   (=bisos.regfps= over =fp=, =bisos.siteRegistrars= over =regfps=) belong
   in their own packages.

If a proposed module doesn't meet all three, it goes in its own package
or in a different umbrella.

* Why an Umbrella (and not one package per module)

BISOS has a history of many small pip packages. Each pays a fixed cost
in scaffolding, versioning cadence, README maintenance, panel directory,
=pypiProc.sh=, and PyPI discoverability. The =fto= + =fp= + =fv= family
is small enough and coherent enough (all filesystem-directory-backed;
all share =FILE_TreeObject= as a base class) that grouping them under
one umbrella is a better trade-off than three sibling packages.

The alternative --- =bisos.fto=, =bisos.fp=, =bisos.fv= as siblings --- is
explicitly *not* what we picked, because:

- They will always be released together.
- They import each other (=fp= inherits from =FILE_TreeObject= in =fto=).
- Their versioning is coupled.
- A user who wants one usually wants the others available.

See also: [[#relation-to-bisosb][Relation to bisos.b]] below for why they will
migrate here rather than staying in =bisos.b=.

* Vocabulary --- Branch, Leaf, Node

A =bisos.fileObj.fto= tree consists of *nodes*. Every node is either a
*branch* or a *leaf*:

- *Node* --- the base concept. Every directory with a planted =_tree_=
  marker file is a node.
- *Branch* --- a node that has children. Has no payload of its own; its
  role is to delegate to the nodes below it.
- *Leaf* --- a node that is a work endpoint. Has whatever payload the
  activity requires (a Dockerfile, an fp store, an image spec).

Additional variants borrowed from the bash reference:

- *auxBranch* --- a branch: skip processing *this branch*, but keep
  traversing into children.
- *auxLeaf* --- a leaf: skip processing *this leaf*, but keep traversing.
- *ignore* --- skip this node and everything below.

Historic terminology note: the bash implementation
(=lcnObjectTree.libSh=) uses *node* to mean what we now call *branch*.
This was a naming choice that predates the clarification "a tree is
made of nodes, and each node is either a branch or a leaf." The Python
implementation writes *branch* going forward but reads bash-written
=_tree_= files that say =node= for backward compatibility.

There is no separate "root" concept. The root is just "whichever branch
the user chose to start from." Any branch can serve as a root; the user's
=cd= sets the root for that invocation.

* Marker Files (from the bash FTO reference)

Every node's directory carries three marker files:

- =_tree_= --- contents identify the node type. Values (from
  =FileTreeItem= enum):
  - =branch= --- a branch (written by Python; bash writes =node=).
  - =leaf= --- a leaf.
  - =auxBranch= / =auxLeaf= --- traverse-but-skip variants.
  - =ignore= --- skip this and everything below.
- =_treeProc_= --- names the executable that processes this node. The
  walker =cat=s this file to discover the processor. Fallback lookup
  order matches the bash reference: =ftoProc.sh= → =_treeProc_= contents
  → the walker's own name.
- =_objectType_= --- optional metadata about the object type (values
  like =fto.node=, =fto.leaf=, =bxt.data=). Lets one walker handle
  heterogeneous trees.

* The Walker

At any branch node, invoking the walker with a command does the
following (mirrors =vis_treeRecurse= in the bash reference):

1. At the current node, apply the command locally.
2. Compute =effectiveLeaves= (declared =leavesList= minus =leavesExcludes=;
   or =leavesOrdered= if set).
3. For each leaf: =cd= in, look up its =_treeProc_=, apply the command.
4. Compute =effectiveBranches= (same shape for =branchesList= /
   =branchesExcludes= / =branchesOrdered=).
5. For each child branch: =cd= in, look up its =_treeProc_=, recurse.

Symlinks are skipped (avoids cycles). Missing =_treeProc_= → skip with
warning. =auxBranch= / =auxLeaf= are traversed but not processed.
=ignore= aborts the subtree.

The walker knows nothing about =.spcs=, containers, or any specific leaf
payload. Consumers register their per-node behavior via =_treeProc_=
files. This is what makes the walker general --- =bro_dockerfiles/= plants
=.spcs= as its =_treeProc_=, but any other tree with a different leaf
type does the same thing with its own processor.

* Motivating Use Case --- .spcs Trees

The immediate consumer is =bisos.dockerProc= and its =bro_dockerfiles=
tree of six leaves (deb12/deb13 × confined/privileged/rootless-sysd
container images). Each leaf has a planted =.spcs= file that drives
build / run / verify for that one container. What that alone cannot do
is run a single command across all six leaves --- or across just the
deb13 leaves, or just the rootless-sysd leaves. That is what
=bisos.fileObj.fto= adds, and it works in that tree today:

- Every branch directory (=debian/=, =debian/13/=, =debian/13/privileged/=,
  ...) gets a planted =ftoBranchProc.spcs=, and =_tree_= = =branch= plus a
  =_treeProc_= naming it. (In =bro_dockerfiles= today all nine branches carry
  the planted =.spcs=; the =_tree_= / =_treeProc_= markers are so far planted
  only at =debian/12/confined/=, which is why a walk reports one branch but
  still reaches all six leaves.)
- Leaves need *no* marker files: the branch passes =leafProcessors= (from
  the consumer's =leafProcessorNames()=) into =ftoBranch_seedInfo.setup()=,
  so a directory containing =dockerProc.spcs= or =podmanProc.spcs= *is* a
  leaf by definition.
- Invoking =./ftoBranchProc.spcs -i fto_forwardToLeaves --cmndName=<verb>=
  from any branch walks that subtree and applies the verb at each leaf
  beneath --- one subprocess per leaf, so one failure does not mask the
  rest.

The tree structure encodes the grouping. Filter-by-flag becomes
filter-by-location. Fully general spread-planted operation.

*Architectural context.* =.spcs= is itself a PyCS-substrate concept
(implemented in =bisos.csSeed=). This package (=bisos.fileObj=) sits
in the middle: substrate below, concrete domain seeds
(=bisos.dockerProc=, =bisos.capability=, future =bisos.lcnt=,
static-web, ...) above. For the three-layer architecture and how the
pieces compose --- including the =WalkExampleSpec= typed-data
mechanism and the leaf-seed-owned =walkExamples()= pattern --- see
[[file:/bisos/git/auth/bxRepos/bisos-pip/pycs/spcs/README.org][=bisos.pycs/spcs/README.org=]]
(the =.spcs= architecture reference, with an overview figure).

*The dependency is strictly one-way.* =bisos.dockerProc= imports
=WalkExampleSpec= from here and hands this package its
=walkExamples()= and =leafProcessorNames()=; this package never
imports =bisos.dockerProc=, and nothing here mentions containers,
Debian releases, or engines. That asymmetry is the point --- see
[[#staying-domain-agnostic][Staying Domain-Agnostic]] below.

*Second real consumer --- CBM leaves.* =bisos.capability='s
=cbmProc.spcs= (planted at CBM tree leaves like
=sys/cbm/collective/hereWeb/airflow/=) exercises the same
=leafProcessors= + =walkExamples()= machinery, but demonstrates a
distinct pattern from =dockerProc=: the =.spcs= is a *pointer* to
a separate CBS executable, not a self-contained processor. The walker
doesn't care --- both patterns are just planted =.spcs= files with
a =_treeProc_= discovered by name. This confirms the walker
abstraction handles both self-contained (=dockerProc=: paths-are-params)
and pointer (=capability=: file-is-target) leaves uniformly.

* Staying Domain-Agnostic
  :PROPERTIES:
  :CUSTOM_ID: staying-domain-agnostic
  :END:

The container work described above involves *four related pieces*, of which
this package is deliberately the most distant. Recording the whole set here so
the boundary is visible from this side:

| Piece                     | Kind        | Job                                                      |
|---------------------------+-------------+----------------------------------------------------------|
| =bisos.fileObj= (*this*)  | pip package | *Generic tree walker.* FTO marker conventions,           |
|                           |             | =ftoBranchProc.spcs=, =fto_forwardToLeaves= /            |
|                           |             | =fto_walkRunExternal=, =WalkExampleSpec=.                |
| =bisos.dockerProc=        | pip package | *Container framework.* Planted =dockerProc.spcs= /       |
|                           |             | =podmanProc.spcs=, path-derived parameters,              |
|                           |             | =containerProc_*= verbs. A *consumer* of this package.   |
| =bro_dockerfiles=         | BRO (repo)  | *Container image specifications.* The tree this walker   |
|                           |             | is planted in. Jointly designed with =bisos.dockerProc=. |
| =/bisos/core/raw/rebuild= | git repo    | *RawBisos-Reconstruction (BISOS's CI/CD)* across boxes,  |
|                           |             | KVM guests and containers. Does *not* use this walker    |
|                           |             | (see below).                                             |

Sources: [[https://github.com/bisos-pip/dockerProc][bisos.dockerProc]],
[[https://github.com/bxObjects/bro_dockerfiles][bro_dockerfiles]],
[[https://github.com/bisos/raw][bisos/raw]].

*Nothing about containers belongs in this package.* The walker's contract is
marker files plus =_treeProc_= dispatch; every domain-specific decision is
delegated to the consumer:

- What counts as a *leaf* --- the consumer supplies =leafProcessors= (the
  =.spcs= filenames that definitionally identify one), so leaves need no
  per-directory =_tree_= marker.
- What is *worth running* at those leaves --- the consumer supplies a list of
  =WalkExampleSpec= records, which the branch's examples menu renders.
- What the verb *does* --- entirely the consumer's leaf-side seed; the walker
  only subprocess-invokes it.

A second consumer already exercises this from a different angle:
=bisos.capability='s =cbmProc.spcs= is a *pointer* to a separate CBS
executable rather than a self-contained processor. The walker cannot tell the
two apart, which is the evidence that the abstraction is at the right level.
Future consumers (=bisos.lcnt=, static-web publication) are expected to add
no special cases here. The one shared vocabulary this package does define is
domain-neutral: the walk modes, and the lifecycle verbs of
[[#generic-lifecycle-verbs][Generic Lifecycle Verbs]].

*Why =rawBuild*= does not use the walker.* Reconstruction addresses its target
by *parameter* --- =freshDeb= plus a platform-specific selector --- not by
location. Its =rawBuildGuest.cs= targets a VAG =bpoId= and its =rawBuildBox.cs=
targets a destination IP address; neither has a tree at all. Only the container
sibling has one. The two are complementary rather than competing: this walker
is *location-addressed and broad* (one verb, every leaf beneath a branch),
while =rawBuild*= is *parameter-addressed and deep* (one target, an ordered
sequence of steps). Both facilities exist because both questions get asked.

* Generic Lifecycle Verbs --- =fto_prepare= ... =fto_status=
  :PROPERTIES:
  :CUSTOM_ID: generic-lifecycle-verbs
  :END:

Implemented 2026-10-26 (Stage 4 of [[file:AI-WorkPlan.org][AI-WorkPlan.org]]; the design was
reviewed and its open points decided --- see "Decisions" below). A first version had been built
inside =bisos.dockerProc= (its Stage 9); the generic part now lives here.

** Why

A walk forwards a verb *by name* (=fto_forwardToLeaves --cmndName=<verb>=) to every leaf below a
branch. Before this, each consumer had its own names for the same ideas --- =cbm_materialize= for
CBM leaves, =containerProc_instanceUp= / =containerProc_reMaterialize= for container leaves --- and
its own copy of the gate that decides whether a leaf may be acted on. So one walk could not bring
a mixed tree up, every consumer re-implemented the gate, and the copies drifted.

The answer is a small *lifecycle vocabulary* defined once, here: seven verbs, a gate, and a
status log, with each consumer supplying only *what the verb does* for its kind of leaf.

*This is not domain vocabulary.* [[#staying-domain-agnostic][Staying Domain-Agnostic]] keeps
containers, engines and releases out of this package, and that holds: "prepare", "materialize"
and "clean" say nothing about what a leaf is. They name stages of a leaf's life, as
=fto_forwardToLeaves= names a way of walking. Whatever a verb means for containers or CBS
bundles stays in the consumer.

** The vocabulary

| Verb                | Means                                             | Runs when the gate is |
|---------------------+---------------------------------------------------+-----------------------|
| =fto_prepare=       | Make ready to run. Non-destructive, idempotent.   | not =disabled=        |
| =fto_materialize=   | Bring to the running state. Idempotent.           | =enabled=             |
| =fto_reMaterialize= | Re-create with the current preparation.           | =enabled=             |
| =fto_unMaterialize= | Take the running state down. Preparation is kept. | =enabled=             |
| =fto_clean=         | Undo =fto_prepare=.                               | =enabled=             |
| =fto_verify=        | Check the leaf is as it should be. Read-only.     | not =disabled=        |
| =fto_status=        | Show the leaf's current state. Read-only.         | not =disabled=        |

For a container leaf, for example: build the image; bring the instance up; re-create a stale
instance; delete the instance; remove the image; the smoke test; inspect + service state. For a
CBM leaf: install the software (sbom); =cbs_materialize=; =cbs_reMaterialize=;
=cbs_unMaterialize=; nothing yet for =clean=.

The contract every consumer keeps:
- *Idempotent where it says so:* =prepare= and =materialize= on a leaf that is already
  prepared / up succeed and change nothing.
- *=reMaterialize= decides itself whether there is anything to do* (e.g. only a stale instance is
  re-created) and says so; it is not "always tear down and rebuild".
- *Unsupported is not failure:* a verb a leaf kind does not implement answers "not supported by
  this leaf kind", succeeds, and logs =skipped: unsupported=. A walk across a mixed tree then
  does not flag every leaf that lacks, say, =clean=.

** The gate and the status log

Each leaf may have two files next to its planted file, named after it (=<plantStem>= is the
planted file's name without its suffix, e.g. =dockerProc=, =podmanProc=, =cbmProc=):

: <leaf>/<plantStem>.control   # one word: enabled | available | disabled
: <leaf>/<plantStem>.status    # appended:  2026-10-26T14:03:07  ran: fto_reMaterialize ok (...)

- =enabled= --- every verb runs.
- =available= --- present, not activated: =prepare=, =verify= and =status= run; the destructive
  verbs (=materialize=, =reMaterialize=, =unMaterialize=, =clean=) skip.
- =disabled= --- *leave this leaf completely alone*: every verb skips, read-only ones included.
- *A missing =.control= file means =available=*: nothing destructive happens to a leaf until
  someone enables it.
- The gate commands always run (else a disabled leaf could not be re-enabled): =fto_control=
  (show), =fto_statusLog= (show the log), =fto_enable=, =fto_available=, =fto_disable=.
- Every run appends one line (=fto_status= excepted): =ran: <verb> ok (<result>)=,
  =skipped: control=<state> at <verb>=, =skipped: unsupported <verb>=, =failed: <verb>: <reason>=,
  and gate changes =control=<state>=. A walk's own failure count is not reliable today (Stage 2's
  exit-code TODO: =bisos.b= exits 0 even when a command fails), so the logs are the record.
- These are exactly CBM's existing =cbmProc.control= / =cbmProc.status= (same states, same
  default, same line style): CBM leaves need no file changes to adopt this.
- *Whether the files are committed is the tree's decision, not this package's.* bro_rawBisos
  commits its =cbmProc.*= (they describe the platform tree); bro_dockerfiles git-ignores its
  =dockerProc.*= / =podmanProc.*= (they describe one VM: one user per VM, each with a clone).

** Leaf side: what a consumer does

1. *Registers its actions once*, in its csu module at import time:

   #+begin_src python
   from bisos.fileObj import ftoLeaf_seedInfo
   ftoLeaf_seedInfo.setup(
       prepare=_imageBuild,              # each: (cmndOutcome) -> b.op.Outcome
       materialize=_materialize,         # the consumer resolves its own leaf parameters
       reMaterialize=_reMaterialize,     # (e.g. from the planted path) inside the action
       unMaterialize=_unMaterialize,
       clean=_imageClean,
       verify=_instanceVerify,
       status=_instanceStatus,           # any verb left out is "unsupported" at this leaf kind
   )
   #+end_src

2. *Adds =bisos.fileObj.ftoLeaf_csu= to its seed's =csuList=* --- in the =csuList= spec, then
   regenerate the =csuListImportPlus= dblock in Blee: it must also *import* the module, because
   PyCS only looks for commands in imported =csuList= modules.

3. *Adds the verbs to its menus*: =ftoLeaf_seedInfo.lifecycleWalkExamples()= returns the
   =WalkExampleSpec= entries, to append to the consumer's =walkExamples()=;
   =ftoLeaf_seedInfo.lifecycleExamplesMenu()= renders a section for the leaf's own menu.

Each =fto_<verb>= then: reads the gate, calls the registered action (or answers "unsupported"),
appends the status line, returns the action's outcome; an exception from an action is logged
=failed:= and re-raised. The leaf's planted file is the seed's =plantOfThisSeed=; a leaf whose
processor is a plain PyCS program (not a seeded =.spcs=) uses the program itself (=sys.argv[0]=).
The consumer keeps its own commands (=containerProc_imageBuild=, =cbm_materialize=, ...); they may
stay as they are or become aliases of the =fto_= ones.

*How PyCS finds commands --- a rule every consumer must follow.* PyCS dispatches a name only if it
is a *top-level class* in the source of an imported =csuList= module *and* a *direct* subclass of
=cs.Cmnd= (=bisos.b.cs.inCmnd.cmndList_mainsMethods= intersects the scanned class names with
=cs.Cmnd.__subclasses__()=). A class deriving from another command class, or made by a factory
function, is never dispatched. So shared behaviour goes in a mixin that is *not* a =cs.Cmnd=:
=class fto_prepare(LifecycleVerbMixin, cs.Cmnd)=, and an alias delegates to its target instead of
deriving from it.

** Branch side: the same names walk

At a branch, =ftoBranchProc.spcs -i fto_<verb>= forwards =fto_<verb>= to every leaf below, hands
the same verb to each sub-branch that has its own =ftoBranchProc.spcs= (so each level runs and
summarizes its own part), and ends with a *summary read back from the leaves' status logs*:

: == fto_prepare at .../debian/13/privileged:  ran=2  skipped=0  failed=0  noLog=0
:   vnc/xfce/bisos_deb13-sysd: ran: fto_prepare ok (Built bisos_deb13-sysd)
:   vnc/xfce/bisos_deb13-sysd-2: ran: fto_prepare ok (No image of its own: ...)

So a verb name means the same thing everywhere --- *at a leaf it acts, at a branch it walks*.
After a change that needs new images, a container tree's two phases read:

#+begin_src bash
cd bro_dockerfiles/debian/13
./ftoBranchProc.spcs -i fto_prepare          # rebuild images, in the branch's order
./ftoBranchProc.spcs -i fto_reMaterialize    # re-create the stale instances of enabled leaves
./ftoBranchProc.spcs -i fto_statusLog        # what happened, leaf by leaf
#+end_src

All twelve names work at a branch (the seven verbs and the five gate commands), with =--path= and
=--recurseMode= as for =fto_forwardToLeaves=.

*Options for the leaves are passed on (2026-11-23).* Any option the branch itself does not
declare --- e.g. a container leaf's =--noCache= --- is passed on unchanged to every leaf and to
every sub-branch (which passes it on in turn), by the lifecycle verbs and by
=fto_forwardToLeaves= alike; the branch prints =forwarding to leaves: ...= first:

#+begin_src bash
./ftoBranchProc.spcs -i fto_prepare --noCache=true
./ftoBranchProc.spcs -i fto_forwardToLeaves --cmndName=containerProc_imageBuild --noCache=true
#+end_src

How: =ftoBranch-seed.cs= runs with =ignoreUnknownParams=True=, so PyCS drops such options; the
forwarding verbs recover them by re-parsing the command line with PyCS's own parser
(=G.icmArgsParser=). Only the =--name=value= form is passed on; =--name value= is refused before
anything runs (once dropped, the value cannot be told from an argument). Before 2026-11-23 these
options were silently lost --- a walked =--noCache=true= built with the cache.

Each leaf then validates them. A leaf whose seed rejects unknown options prints =error:
unrecognized arguments= and does nothing; PyCS still exits 0, so such a leaf shows as =noLog= in a
lifecycle summary and is *not* counted as failed by =fto_forwardToLeaves= --- read the output.
argparse also accepts an unambiguous prefix (=--noCach= is =--noCache=). Whether a leaf acts on a
passed-on option is the consumer's business (=bisos.dockerProc='s =fto_prepare= honours
=--noCache=).

*Order* matters for =prepare= (an image built =FROM= another): a branch's =branchesOrdered= /
=leavesOrdered= express it. Those lists are taken verbatim as names of the branch's *direct*
children, so they do not reach leaves one or more plain directories below; to order those, plant
a branch file at their level --- or see Stage 3's =childNodesOrdered=. Without a list, children are
walked in sorted order.

** Decisions (review of 2026-10-26)

1. =disabled= means *leave this leaf completely alone*: it blocks every verb, the non-destructive
   ones included; =available= lets =prepare= / =verify= / =status= run.
2. Branch-side verbs end with a summary read back from the leaves' status logs.
3. Module names: =ftoLeaf_seedInfo= (gate, log, registration, mixins, menus) and =ftoLeaf_csu= (the
   leaf commands).
4. The set: the five lifecycle verbs plus =fto_verify= and =fto_status=.

* Relation to bisos.b

Today =bisos.b= contains =b.fto=, =b.fp=, =b.fv=, and =b.fpCls= as
sibling modules. All four are filesystem-directory-backed data
structures. =b.fto= has a =FILE_TreeObject= class shell with most walker
methods stubbed out; =b.fp= and =b.fv= are working implementations with
50+ importers in downstream BISOS packages.

*=bisos.b= should be as small as possible.* It is the PyCS foundation
that nearly every bisos-pip package depends on; anything not truly
foundational should live elsewhere. The =fto= / =fp= / =fv= family fits
that description --- they are useful primitives but not part of PyCS
itself.

*Migration plan:*
- *Stage 1 (now)*: Create =bisos.fileObj= with =fto= as its first module,
  properly implementing the walker (which =b.fto= only stubs). No changes
  to =bisos.b= yet.
- *Later, in separate work*: Migrate =b.fp= and =b.fv= into
  =bisos.fileObj.fp= / =bisos.fileObj.fv=. Leave one-line compatibility
  shims in =bisos.b.fp= / =bisos.b.fv= that re-export from
  =bisos.fileObj= for the 50+ existing importers. Eventually remove the
  shims.

Until that migration lands, =bisos.fileObj.fp= and =bisos.fileObj.fv= are
reserved slots --- documented here so no one plants a differently-named
module there in the interim.

* Relation to the bash FTO reference

The bash implementation lives at:

- =/bisos/core/bsip/bin/lcnObjectTree.libSh= --- the library (620 lines).
  Defines the vocabulary, marker file enums, walker.
- =/bisos/core/bsip/bin/seedFtoCommon.sh= --- the seed that sources the
  library and provides examples/dispatch (1270 lines).
- =/bisos/core/bsip/bin/ftoProc.sh=, =startAnyFto.sh= --- user-facing
  entry points.

Example usage: =/bisos/git/bxRepos/bisos-pip/ftoProc.sh= plants an FTO
walker at the top of the bisos-pip tree with =nodesList= naming each
Python package directory (=b=, =banna=, =bpo=, ...) --- one command from
there walks and applies to all packages.

=bisos.fileObj.fto= is a Python port of that model. Same vocabulary
(corrected: branch/leaf, not node/leaf), same marker file conventions,
same walker semantics. Not a replacement; a peer that operates on the
same tree conventions. A tree can be walked by either implementation.

* Usage

** As a Python library

#+begin_src python
from bisos.fileObj import fto

# Create a tree
branch = fto.FILE_TreeObject('/tmp/exampleTree')
branch.branchCreate()

leaf = fto.FILE_TreeObject('/tmp/exampleTree/leaf1')
leaf.leafCreate()

# Walk the tree, applying a command at each node
fto.treeRecurse(base='/tmp/exampleTree', command=['echo', 'hello'])
#+end_src

** As a walker

Plant a branch =.spcs= at any branch directory in your tree, then invoke
it with a command. The walker descends into every leaf beneath that
branch and applies the command via each leaf's =_treeProc_=.

See the =bisos.dockerProc= + =bro_dockerfiles= combination for a
worked-through example.
