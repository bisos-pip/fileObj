* Overview

/bisos.fileObj/ is an *umbrella package for filesystem-directory-backed
data structures* in BISOS. Each module inside is a self-contained
abstraction whose identity and state live in a filesystem directory, not
in a database or in memory.

Currently:

- =bisos.fileObj.fto= --- *File Tree Object* + tree walker. A generalization
  of the bash-based FTO facility (=/bisos/core/bsip/bin/lcnObjectTree.libSh=,
  =seedFtoCommon.sh=, =ftoProc.sh=). Marker-file conventions (=_tree_=,
  =_treeProc_=, =_objectType_=), branch/leaf classification, and a walker
  that recurses down a tree applying a command at each node. This is the
  first module and the reason the umbrella package exists.
- =bisos.fileObj.fp= --- *File Parameter*. Currently in =bisos.b.fp=;
  reserved slot for a future migration into this package.
- =bisos.fileObj.fv= --- *File Variable*. Currently in =bisos.b.fv=;
  reserved slot for a future migration.

/bisos.fileObj/ is a python package that uses the [[https://github.com/bisos-pip/pycs][PyCS-Framework]].

* Charter --- Scope of This Package

*This package is for filesystem-directory-backed data structures where the
directory IS the object identity.* If your thing needs a database, an
in-memory structure, or a network resource, it doesn't belong here.

The charter is deliberately narrow so the umbrella does not become a
"small utility drawer." Additions require that the thing being added:

1. Represents its identity and state as a filesystem directory.
2. Uses marker files (like =_tree_=) to make its type / role discoverable.
3. Sits at a similar level of abstraction as =fto=, =fp=, =fv= --- primitive
   data structures, not higher-level constructs. Higher-level things
   (=bisos.regfps= over =fp=, =bisos.siteRegistrars= over =regfps=) belong
   in their own packages.

If a proposed module doesn't meet all three, it goes in its own package
or in a different umbrella.

* Why an Umbrella (and not one package per module)

BISOS has a history of many small pip packages. Each pays a fixed cost
in scaffolding, versioning cadence, README maintenance, panel directory,
=pypiProc.sh=, and PyPI discoverability. The =fto= + =fp= + =fv= family
is small enough and coherent enough (all filesystem-directory-backed;
all share =FILE_TreeObject= as a base class) that grouping them under
one umbrella is a better trade-off than three sibling packages.

The alternative --- =bisos.fto=, =bisos.fp=, =bisos.fv= as siblings --- is
explicitly *not* what we picked, because:

- They will always be released together.
- They import each other (=fp= inherits from =FILE_TreeObject= in =fto=).
- Their versioning is coupled.
- A user who wants one usually wants the others available.

See also: [[#relation-to-bisosb][Relation to bisos.b]] below for why they will
migrate here rather than staying in =bisos.b=.

* Vocabulary --- Branch, Leaf, Node

A =bisos.fileObj.fto= tree consists of *nodes*. Every node is either a
*branch* or a *leaf*:

- *Node* --- the base concept. Every directory with a planted =_tree_=
  marker file is a node.
- *Branch* --- a node that has children. Has no payload of its own; its
  role is to delegate to the nodes below it.
- *Leaf* --- a node that is a work endpoint. Has whatever payload the
  activity requires (a Dockerfile, an fp store, an image spec).

Additional variants borrowed from the bash reference:

- *auxBranch* --- a branch: skip processing *this branch*, but keep
  traversing into children.
- *auxLeaf* --- a leaf: skip processing *this leaf*, but keep traversing.
- *ignore* --- skip this node and everything below.

Historic terminology note: the bash implementation
(=lcnObjectTree.libSh=) uses *node* to mean what we now call *branch*.
This was a naming choice that predates the clarification "a tree is
made of nodes, and each node is either a branch or a leaf." The Python
implementation writes *branch* going forward but reads bash-written
=_tree_= files that say =node= for backward compatibility.

There is no separate "root" concept. The root is just "whichever branch
the user chose to start from." Any branch can serve as a root; the user's
=cd= sets the root for that invocation.

* Marker Files (from the bash FTO reference)

Every node's directory carries three marker files:

- =_tree_= --- contents identify the node type. Values (from
  =FileTreeItem= enum):
  - =branch= --- a branch (written by Python; bash writes =node=).
  - =leaf= --- a leaf.
  - =auxBranch= / =auxLeaf= --- traverse-but-skip variants.
  - =ignore= --- skip this and everything below.
- =_treeProc_= --- names the executable that processes this node. The
  walker =cat=s this file to discover the processor. Fallback lookup
  order matches the bash reference: =ftoProc.sh= → =_treeProc_= contents
  → the walker's own name.
- =_objectType_= --- optional metadata about the object type (values
  like =fto.node=, =fto.leaf=, =bxt.data=). Lets one walker handle
  heterogeneous trees.

* The Walker

At any branch node, invoking the walker with a command does the
following (mirrors =vis_treeRecurse= in the bash reference):

1. At the current node, apply the command locally.
2. Compute =effectiveLeaves= (declared =leavesList= minus =leavesExcludes=;
   or =leavesOrdered= if set).
3. For each leaf: =cd= in, look up its =_treeProc_=, apply the command.
4. Compute =effectiveBranches= (same shape for =branchesList= /
   =branchesExcludes= / =branchesOrdered=).
5. For each child branch: =cd= in, look up its =_treeProc_=, recurse.

Symlinks are skipped (avoids cycles). Missing =_treeProc_= → skip with
warning. =auxBranch= / =auxLeaf= are traversed but not processed.
=ignore= aborts the subtree.

The walker knows nothing about =.spcs=, containers, or any specific leaf
payload. Consumers register their per-node behavior via =_treeProc_=
files. This is what makes the walker general --- =bro_dockerfiles/= plants
=.spcs= as its =_treeProc_=, but any other tree with a different leaf
type does the same thing with its own processor.

* Motivating Use Case --- .spcs Trees

The immediate consumer is =bisos.dockerProc= and its =bro_dockerfiles=
tree of six leaves (deb12/deb13 × confined/privileged/rootless-sysd
container images). Each leaf has a planted =.spcs= file that drives
build / run / verify for that one container. What's missing today is
the ability to run a single command across all six leaves --- or across
just the deb13 leaves, or just the rootless-sysd leaves.

With =bisos.fileObj.fto=:
- Every leaf directory gets a =_tree_= file with =leaf= and a =_treeProc_=
  naming the planted =.spcs= file.
- Intermediate directories (=debian/13/=, =debian/=, =bro_dockerfiles/=)
  get =_tree_= with =branch= and a =_treeProc_= naming a branch =.spcs=.
- Invoking =./someBranchProc.spcs -i containerProc_imageBuild= from any
  branch walks that subtree and applies the command at each leaf beneath.

The tree structure encodes the grouping. Filter-by-flag becomes
filter-by-location. Fully general spread-planted operation.

*Architectural context.* =.spcs= is itself a PyCS-substrate concept
(implemented in =bisos.csSeed=). This package (=bisos.fileObj=) sits
in the middle: substrate below, concrete domain seeds
(=bisos.dockerProc=, future =bisos.lcnt=, static-web, ...) above. For
the three-layer architecture and how the pieces compose --- including
the =WalkExampleSpec= typed-data mechanism and the leaf-seed-owned
=walkExamples()= pattern --- see
[[file:/bisos/git/auth/bxRepos/bisos-pip/pycs/spcs/README.org][=bisos.pycs/spcs/README.org=]]
(the =.spcs= architecture reference, with an overview figure).

* Relation to bisos.b

Today =bisos.b= contains =b.fto=, =b.fp=, =b.fv=, and =b.fpCls= as
sibling modules. All four are filesystem-directory-backed data
structures. =b.fto= has a =FILE_TreeObject= class shell with most walker
methods stubbed out; =b.fp= and =b.fv= are working implementations with
50+ importers in downstream BISOS packages.

*=bisos.b= should be as small as possible.* It is the PyCS foundation
that nearly every bisos-pip package depends on; anything not truly
foundational should live elsewhere. The =fto= / =fp= / =fv= family fits
that description --- they are useful primitives but not part of PyCS
itself.

*Migration plan:*
- *Stage 1 (now)*: Create =bisos.fileObj= with =fto= as its first module,
  properly implementing the walker (which =b.fto= only stubs). No changes
  to =bisos.b= yet.
- *Later, in separate work*: Migrate =b.fp= and =b.fv= into
  =bisos.fileObj.fp= / =bisos.fileObj.fv=. Leave one-line compatibility
  shims in =bisos.b.fp= / =bisos.b.fv= that re-export from
  =bisos.fileObj= for the 50+ existing importers. Eventually remove the
  shims.

Until that migration lands, =bisos.fileObj.fp= and =bisos.fileObj.fv= are
reserved slots --- documented here so no one plants a differently-named
module there in the interim.

* Relation to the bash FTO reference

The bash implementation lives at:

- =/bisos/core/bsip/bin/lcnObjectTree.libSh= --- the library (620 lines).
  Defines the vocabulary, marker file enums, walker.
- =/bisos/core/bsip/bin/seedFtoCommon.sh= --- the seed that sources the
  library and provides examples/dispatch (1270 lines).
- =/bisos/core/bsip/bin/ftoProc.sh=, =startAnyFto.sh= --- user-facing
  entry points.

Example usage: =/bisos/git/bxRepos/bisos-pip/ftoProc.sh= plants an FTO
walker at the top of the bisos-pip tree with =nodesList= naming each
Python package directory (=b=, =banna=, =bpo=, ...) --- one command from
there walks and applies to all packages.

=bisos.fileObj.fto= is a Python port of that model. Same vocabulary
(corrected: branch/leaf, not node/leaf), same marker file conventions,
same walker semantics. Not a replacement; a peer that operates on the
same tree conventions. A tree can be walked by either implementation.

* Usage

** As a Python library

#+begin_src python
from bisos.fileObj import fto

# Create a tree
branch = fto.FILE_TreeObject('/tmp/exampleTree')
branch.branchCreate()

leaf = fto.FILE_TreeObject('/tmp/exampleTree/leaf1')
leaf.leafCreate()

# Walk the tree, applying a command at each node
fto.treeRecurse(base='/tmp/exampleTree', command=['echo', 'hello'])
#+end_src

** As a walker

Plant a branch =.spcs= at any branch directory in your tree, then invoke
it with a command. The walker descends into every leaf beneath that
branch and applies the command via each leaf's =_treeProc_=.

See the =bisos.dockerProc= + =bro_dockerfiles= combination for a
worked-through example.
