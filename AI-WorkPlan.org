* Stage 1: Package Scaffolding and =fto= Walker Foundation

Goal: Establish =bisos.fileObj= as a working pip package with =fto= as its
first module. Deliver a Python walker that parallels the bash reference
(=/bisos/core/bsip/bin/lcnObjectTree.libSh= + =seedFtoCommon.sh=). The
walker's job: given a starting directory (any branch), recurse the tree
using =_tree_= / =_treeProc_= / =_objectType_= marker files, applying a
command at each node.

The vocabulary correction is a Stage 1 commitment: the Python
implementation writes *branch* / *leaf* / *auxBranch* / *auxLeaf* from
day one, reads legacy bash =node= / =auxNode= for backward compatibility.

The walker knows nothing about =.spcs= or any specific leaf payload.
Consumers register per-node behavior via =_treeProc_= files. This is
the abstraction ceiling for Stage 1.

** Design Decisions Captured in this Stage

These decisions came out of extended discussion before Stage 1 began.
Recording them here so future-Claude does not re-relitigate:

1. *Package name is =bisos.fileObj=, not =bisos.fto=.* Chosen as an
   umbrella for future filesystem-directory-backed data structures (fp,
   fv). Rationale: BISOS has too many small pip packages; a small
   umbrella with a *tight, written charter* (see README) is preferable
   to sibling packages =bisos.fp= / =bisos.fv= / =bisos.fto=.

2. *Charter is narrow:* filesystem-directory-backed data structures
   where the directory IS the object identity. Not a general utility
   drawer. Additions must meet all three criteria in the README's
   Charter section.

3. *Vocabulary: branch/leaf, not node/leaf.* The bash reference uses
   =node= to mean what we call =branch= --- this is a historic mistake we
   are correcting in the Python port. Python writes =branch= going
   forward; reads =node= from bash-written files for compatibility.
   No "root" concept as a first-class thing --- root is wherever the user
   chose to start walking from.

4. *=bisos.b= is not touched in Stage 1.* No modifications to =b.fto=,
   =b.fp=, =b.fv=, =b.fpCls=. Their eventual migration into
   =bisos.fileObj.fp= / =fv= is Stage-N work, out of scope now. See
   README "Relation to bisos.b" for the migration plan.

5. *The walker does not know about =.spcs=.* It only knows about
   =_treeProc_= files (which a =.spcs= file may register itself as, but
   so may any other executable). This layering keeps =bisos.fileObj.fto=
   general.

6. *Marker files: three, per the bash reference.* =_tree_= (contents:
   =branch= / =leaf= / =auxBranch= / =auxLeaf= / =ignore=), =_treeProc_=
   (contents: name of the executable that processes this node),
   =_objectType_= (optional: type metadata for heterogeneous trees).

7. *Branch =.spcs= dispatch is transparent (Option A).* A branch
   =.spcs= (=ftoBranchProc.spcs=) exposes two kinds of Cmnds:
   - =fto_*= Cmnds (=fto_nodeInfo=, =fto_effectiveLeaves=, etc.) run
     *locally* at the branch --- they introspect or manipulate this
     specific branch.
   - Any other =-i <cmndName>= is *transparently forwarded* to the
     walker, which recurses and invokes each descendant leaf's
     =_treeProc_ -i <cmndName>=. The branch =.spcs= doesn't need to
     know what commands its descendants support; it just forwards.
   Matches the bash reference (=ftoProc.sh -i treeRecurse gitStatusReport=
   → walks and runs =gitStatusReport= at each descendant).

8. *Branch =.spcs= naming: =ftoBranchProc.spcs=.* Parallels the bash
   =ftoProc.sh= naming. The =Proc= suffix signals "this file processes
   the branch." Ships in =bisos.fileObj/py3/bin/=; consumers copy or
   symlink it into their trees at branch positions (same pattern as
   =dockerProc.spcs= is planted from =bisos.dockerProc/py3/bin/=).

9. *Membership resolution: autodiscover + explicit override (Both).*
   By default, the walker discovers children by scanning directories
   with =_tree_= markers. Dot-directories and =_*_= metadata dirs
   (like =_nodeBase_=) are skipped by convention. A branch =.spcs=
   MAY declare its own module-level control parameters
   (=branchesList=, =leavesList=, =branchesExcludes=, =leavesExcludes=,
   =branchesOrdered=, =leavesOrdered=) --- exactly as =ftoProc.sh= does
   with bash variables. When present, these override autodiscover.
   Stage 1 initial cut only needs autodiscover; the walker's function
   signatures reserve the parameters so control-parameter support is a
   drop-in later.

10. *=.spcs= files are real Python files.* They are not thin wrappers
    that only read cwd --- a =.spcs= can declare module-level parameters,
    functions, exclusion lists, whatever it needs. This mirrors the bash
    reference: =/bxRepos/bisos-pip/ftoProc.sh= has =leavesList=,
    =nodesList=, =nodesExcludes=, etc. as bash variables at module
    level. The Python =.spcs= equivalent uses the same variable names as
    Python module-level values.

** TODO [#A] Implement =bisos.fileObj.fto=: walker (=treeRecurse=, =effectiveBranches=, =effectiveLeaves=) :ai:
SCHEDULED: <2026-08-12 Wed>
Second half of the walker work in =py3/bisos/fileObj/fto.py=. This is
the recursion engine. Bash reference: =vis_treeRecurse=,
=vis_effectiveLeaves=, =vis_effectiveNodes= in =lcnObjectTree.libSh=.

Functions to implement:

- =effectiveBranches(basePath, branchesList=None, branchesExcludes=None,
  branchesOrdered=None) -> list[Path]= --- pure function returning the
  ordered list of child branch directories. If =branchesOrdered= is
  given, use it verbatim. Otherwise compute =set(branchesList) -
  set(branchesExcludes)= and sort. If neither given, autodiscover:
  every child directory that has a =_tree_= file marking it as
  =Branch= or =AuxBranch=.
- =effectiveLeaves(basePath, leavesList=None, leavesExcludes=None,
  leavesOrdered=None) -> list[Path]= --- same shape for leaves.
- =branchPredicate(path) -> bool= --- true if =path/_tree_= exists and
  contains =branch= (or bash =node=).
- =leafPredicate(path) -> bool= --- same for =leaf=.
- =treeRecurse(basePath, command, applyAtBranch=True, applyAtLeaf=True,
  skipSymlinks=True) -> WalkResult= --- the main walker.
  1. If current node is =Ignore=, return early with skipped=True.
  2. If =applyAtBranch= and current is a branch (or auxBranch skips
     processing here but recurses), apply command via node's
     =_treeProc_=.
  3. For each leaf in =effectiveLeaves()=: apply command via leaf's
     =_treeProc_=. AuxLeaf → skip application. Ignore → skip whole.
  4. For each child branch in =effectiveBranches()=: recurse.
     Symlink branches → skip (cycle avoidance).
- =WalkResult= dataclass: per-node PASS/FAIL/SKIP status, aggregated.
  Continues on failure (like bash =vis_treeRecurse=) --- one bad node
  does not abort the whole walk.

Command dispatch: how a command is applied depends on the =_treeProc_=
value. Options to support (start with the simplest):
- If =_treeProc_= names an executable on =PATH= or in the node dir,
  invoke via =subprocess=.
- Support a "callable" form where the caller passes a Python function
  that receives the node's =FILE_TreeObject= --- for in-process walks
  that don't need to shell out.

** TODO [#A] =fto_csu.py=: node-introspection Cmnds (=fto_*= surface) :ai:
SCHEDULED: <2026-08-12 Wed>
Rewrite =py3/bisos/fileObj/fto_csu.py=. Two Cmnd groups: introspection
(this TODO) and creation (next TODO). Introspection group operates on
the *current* node (cwd or =--path==) and reports:

| Cmnd                     | Purpose                                                     |
|--------------------------+-------------------------------------------------------------|
| =fto_nodeInfo=           | Print =_tree_= + =_treeProc_= + =_objectType_= at target    |
| =fto_effectiveBranches=  | Print the effective child branches at target                |
| =fto_effectiveLeaves=    | Print the effective child leaves at target                  |
| =fto_leafPredicate=      | Exit 0 if target is a leaf; 1 otherwise                     |
| =fto_branchPredicate=    | Exit 0 if target is a branch; 1 otherwise                   |
| =fto_treeList=           | List every node beneath target (dry-run of =treeRecurse=)   |

The =fto_= prefix is meaningful: at a branch =.spcs=, these Cmnds run
*locally* (against this branch) rather than being forwarded to leaves.
See Design Decision 7 above.

CS param registration in =commonParamsSpecify=: =path= (target
directory; defaults to cwd), =treeProc= (name of the =_treeProc_= to
write when needed), =objectType= (name of the =_objectType_= to write).

=examples_csu()= for this TODO shows the introspection surface.

** TODO [#A] =ftoBranchProc.spcs=: the branch-side spread-planted CS :ai:
SCHEDULED: <2026-08-12 Wed>
New file =py3/bin/ftoBranchProc.spcs= --- the branch-side companion to
future leaf =.spcs= files. Ships in =bisos.fileObj/py3/bin/=; consumers
copy or symlink it into their trees at branch positions.

Behaviour:
1. On import (=from bisos.fileObj import fto=), the =.spcs= reads its
   own location via =seedsLib.seededCsxuInfo.plantOfThisSeed=. That's
   the branch's directory.
2. Dispatch on the =-i <cmndName>= argument (Design Decision 7):
   - If =cmndName= starts with =fto_= → run locally against this
     branch (via the =fto_csu= surface).
   - Else → treat as a *leaf command name*. Invoke =treeRecurse=,
     which walks the effective leaves beneath this branch and calls
     each leaf's =_treeProc_ -i <cmndName>= (forwarding any extra
     args/params).

Bare invocation (no =-i=) shows an examples menu filtered for what
this branch actually contains --- =fto_= introspection commands plus a
"forwarded commands" section showing whatever the leaves support (best
effort: introspect one leaf's =_treeProc_= for its examples, and
suggest common Cmnd names).

May declare module-level control parameters (=branchesList=,
=leavesList=, =branchesExcludes=, =leavesExcludes=, =branchesOrdered=,
=leavesOrdered=) --- see Design Decision 9. Stage 1 initial cut relies
on autodiscover; the machinery is reserved for future planted branches
that need explicit control.
