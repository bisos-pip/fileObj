* Architecture

Six hand-authored files, all in COMEEGA/dblock format:

** =py3/bisos/fileObj/= (Python package)

- =fto.py= — pure walker library (=cs-lib= classification).
  Provides =FileTreeItem= enum (=Branch=, =Leaf=, =AuxBranch=,
  =AuxLeaf=, =Ignore=), =FILE_TreeObject= class (node create/read/predicate
  methods), and walker functions (=branchPredicate=, =leafPredicate=,
  =effectiveBranches=, =effectiveLeaves=, =treeRecurse=, =WalkResult=).
  Reads legacy bash =node= / =auxNode= for backward compatibility; writes
  =branch= / =auxBranch= going forward.

- =fto_csu.py= — CS-Lib exposing =fto_*= Cmnds (=cs-lib= classification).
  Three Cmnd groups:
  - *Introspection:* =fto_nodeInfo=, =fto_branchPredicate=,
    =fto_leafPredicate=, =fto_effectiveBranches=, =fto_effectiveLeaves=,
    =fto_treeList=.
  - *Creation:* =fto_branchCreate=, =fto_leafCreate=,
    =fto_auxBranchCreate=, =fto_auxLeafCreate=, =fto_ignoreCreate=.
  - *Forwarding (Stage 2):* =fto_forwardToLeaves= (Mode 1 --- forwards
    =-i <cmndName>= to each leaf's =_treeProc_=), =fto_walkRunExternal=
    (Mode 2 --- runs an arbitrary external cmnd at every visited node,
    with per-node =shutil.which=/=<nodeDir>/cmnd= "perhapsRun"
    resolution).
  Plus =examples_csu= (Cmnd) and =commonParamsSpecify=
  (=path=, =treeProc=, =objectType=, =cmndName= parameters). Every Cmnd
  authored via =b:py3:cs:cmnd/classHead= dblock, fully expanded.
  =examples_csu= now renders leaf-provided walk examples from
  =ftoBranchSeedInfo.leafExamples= as proper =cs.examples.cmndEnter=
  entries (see Deliverable 4 under "Key Design Decisions").

- =ftoBranch_seedInfo.py= — SeedInfo (=cs-u= classification).
  =BranchParams= dataclass; =paramsFromPlantPath()= (trivial-path case:
  branch is =resolve().parent= of the planted =.spcs=);
  =WalkExampleSpec= dataclass (Stage 2: =cmndName=, =pars=, =args=,
  =comment=, =mode=, =tags=); =FtoBranchSeedInfo= singleton with fields:
  =branchesList=, =leavesList=, =branchesExcludes=, =leavesExcludes=,
  =branchesOrdered=, =leavesOrdered=, =examplesFuncsList= (callable
  escape-hatch hook), =leafExamples= (typed data list from leaf-side
  seed). =setup()= populates the singleton from a =.spcs= call.

- =ftoBranch_seed.py= — atexit registrar (minimal). Registers
  =plantWithWhich('ftoBranch-seed.cs')= via =@atexit.register=.

** =py3/bin/= (executables)

- =ftoBranch-seed.cs= — seed CSXU (=cs-mu= classification).
  Full COMEEGA header chain. Imports =csxuFps_csu=, =fto_csu=,
  =ftoBranch_seedInfo=, and =plantedCsu= when planted. Uses
  =csuListProc= dblock. =examples= Cmnd calls
  =fto_csu.examples_csu().pyCmnd()=, then iterates
  =examplesFuncsList= (callable hook, wrapped in =try/except=), then
  runs =plantedCsuExamplesRun()= if a plant is active. Uses
  =ignoreUnknownParams=True=.

- =ftoBranchProc.spcs= — thin stub template (~26 lines).
  Imports =ftoBranch_seed= for the atexit hook. Optional
  =ftoBranch_seedInfo.setup(...)= call commented as an example. This
  file ships in =py3/bin/= as a template; consumers copy it to a
  branch position and customize (e.g. adding
  =setup(leafExamples=containerProc_seedInfo.walkExamples())=).

* Key Design Decisions

**Vocabulary: branch/leaf, not node/leaf.** The bash reference at
=/bisos/core/bsip/bin/lcnObjectTree.libSh= uses =node= to mean what a
proper tree data structure calls a =branch=. Python port writes
=branch= going forward; reads bash-written =node= for compatibility.
No first-class =root= concept — root is wherever the user chose to
start walking.

**Explicit forwarding Cmnd, not transparent dispatch (2026-08-13).**
The =ftoBranchProc.spcs= is a pure pass-through to the seed
(=dockerProc.spcs= pattern). It does NOT inspect the =-i <cmnd>= name
and forward unknown Cmnds to leaves. Instead, forwarding will be an
explicit =fto_forwardToLeaves= Cmnd (Stage 2). Rationale: keeps the
.spcs a genuine thin stub matching the bisos-pip convention.

**Branch =.spcs= uses trivial-path resolution.** The plant path itself
IS the parameter — no anchor-segment parsing like
=containerProc_seedInfo.paramsFromPlantPath()= does with =debian/=. For
=ftoBranchProc.spcs=, =branchPath = Path(plantOfThisSeed).resolve().parent=.
The skill =spread-seeded-cs-commands= should be updated to cover this
"trivial path" case; noted for future work.

**COMEEGA everywhere.** Every hand-authored source file carries the
full COMEEGA header dblock chain (=dblockControls=, =proclamations=,
=particulars=, =particulars-csInfo=, =orgTopControls=, =workbench=,
=framework/imports=, etc.). Every =cs.Cmnd= class is authored via
=b:py3:cs:cmnd/classHead= dblock, fully expanded (matches Blee's
regenerated form). This is a correction from the previous Claude's
draft, which had hand-authored Cmnd classes without dblock structure.
Rule now captured in the new =comeega-authorship= skill and in the
=bisos-pip-setup-py= skill's "Mandatory COMEEGA dblock structure"
section.

**Never hand-edit setup.py / pyproject.toml / _description.org /
README.rst.** All four are regenerated by =pypiProc.sh=. Rule now
captured in the =bisos-pip-setup-py= skill frontmatter and top section.
=README.org= at the repo root is the only authored README.

**bisos.fileObj as an umbrella package.** Charter is
filesystem-directory-backed data structures. =fto= is the first module;
future modules (=fp=, =fv= migrating from =bisos.b=) will join.
See AI-WorkPlan.org "Stage N (Reserved)" and README.org Charter section.

**Two orthogonal walk modes (Stage 2, 2026-08-13).** Following the
bash reference's =treeRecurse= vs =ftoWalkRunCmnd= distinction:
- *Mode 1* (=fto_forwardToLeaves --cmndName=X=): at each effective
  leaf, invoke =<leafDir>/<_treeProc_> -i X=. The verb is a Cmnd name
  the leaf's own dispatcher understands.
- *Mode 2* (=fto_walkRunExternal <cmnd> [args...]=): at each visited
  node, invoke an external cmnd. Node's =_treeProc_= is used only as
  a marker (leaf vs auxLeaf) --- the external cmnd supplies its own
  executable. Matches bash =perhapsRun= semantics: skip silently if
  the cmnd isn't resolvable from the node dir or PATH.
- No unified "smart" forwarder --- callers pick the mode explicitly.

**Leaf-seed-owned walk examples (Stage 2, Deliverable 4).** The
source of truth for "which leaf verbs make sense to walk with" is the
*leaf-side seed*, not the branch =.spcs=. Concretely,
=bisos.dockerProc.containerProc_seedInfo.walkExamples()= returns a list
of =WalkExampleSpec= entries. The branch =.spcs= imports that function
and passes the result to =ftoBranch_seedInfo.setup(leafExamples=...)=.
Adding a new =containerProc_*= Cmnd requires updating =walkExamples()=
once; every branch under =bro_dockerfiles= picks it up on next menu
render. Design decisions locked: D1(c) (branch =.spcs= does the import;
no subprocess bridge yet), D2(a) (=WalkExampleSpec= dataclass lives in
=bisos.fileObj=).

*Deliverable 3 reclassified (2026-08-13).* An earlier design
(Deliverable 3 in AI-WorkPlan) shipped =examplesFuncsList= --- an
arbitrary-callable hook that lets a branch =.spcs= emit any menu
content via =cs.examples.execInsert()=. It was initially the primary
mechanism for domain-specific examples. Deliverable 4 corrects that:
the callable hook is *superseded in role* (typed =leafExamples= is
the primary path) but *retained in code* (Test 6 in verify.sh still
exercises it) as an escape hatch for cases where typed data can't
express what the branch wants (arbitrary chapter headings, prose
blurbs, custom entries).

**=_applyCommand= precedence: planted-copy wins over PATH
(2026-08-13).** Bug discovered during first T2 test with
=bro_dockerfiles/debian/12/confined/=: the walker resolved a leaf's
=_treeProc_= value via =shutil.which()= *first*, then fell back to
the node dir. Wrong direction --- "spread planted" contract is that
each leaf's own copy is authoritative. Fixed in =fto.py:436-448=.

**=_resolveList= excludes must apply to autodiscover too
(2026-08-13).** Second bug found during Test 7: excludes were only
honored when =listed= was also given; pure-excludes-with-autodiscover
was silently ignored. Fixed to apply excludes uniformly to whichever
candidate set (listed or autodiscover) is in play.

**Exit-code propagation limitation (known, deferred).**
=bisos.b.cs.main.g_csMain= exits 0 even when a Cmnd raises, which
means =WalkResult.failed= under-reports leaf failures. Fixing this is
a =bisos.b= concern (upstream); tracked as Stage 2 #C TODO.

: from bisos.fileObj import ftoBranch_seedInfo

:     leafExamples=containerProc_seedInfo.walkExamples(),

=node= vocabulary, pointing at =ftoProc.sh=) are left alone. Bash and
PyCS FTO systems coexist by not sharing =_tree_=/=_treeProc_= files.
